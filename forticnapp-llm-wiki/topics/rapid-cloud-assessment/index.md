## Overview

The FortiCNAPP Rapid Cloud Assessment (RCA) tool is a field instrument used by SE, CSM, and PreSales teams to turn a live FortiCNAPP (Lacework) tenant into a customer-ready security story in minutes rather than days. It exists in two complementary implementation tracks that share one data source — the FortiCNAPP API — but target different delivery surfaces.

**Architecture — Node.js dashboard track.** The production surface is `rca_ui/server.js`, a single ~10,900-line Node.js file with no npm dependencies, no `package.json`, and no bundler [src: claude-md]. It glues two programs into one file: a Node.js HTTP server that polls the FortiCNAPP v2 API, and a browser dashboard whose entire HTML/CSS/JS payload is emitted as one giant template literal by the server's `buildHtml()` function and executed client-side [src: function-reference]. An in-memory `cache` object is written to `/app/data/cache.json` after every `refreshData()` cycle and reloaded on startup, so the dashboard shows last-known-good data instantly instead of blank panels while a fresh fetch runs in the background [src: claude-md]. The API client layer handles token caching (`ensureToken`, ~56-minute lifetime just under Lacework's 1-hour expiry), 429-aware retries that read the `RateLimit-Reset` header, and manual DNS probing (`tcpReachable`/`resolveReachableIP`) to dodge unreachable-but-resolvable IPs [src: function-reference]. Report rendering invokes headless Chromium (installed in the container, always run with `--no-sandbox`) to turn HTML templates into PDFs; four report formats (`/report`, `/report2`, `/report3`, `/report4`) coexist, each independently maintained [src: claude-md].

**Architecture — Python reporting track.** A parallel `extensible-reporting` pipeline uses Python (`pandas`, `jinja2`, `plotly`, `kaleido`, `weasyprint`, `laceworksdk`) to produce auto-generated Cloud Security Assessment reports — the lambda bundle lists `laceworksdk` for FortiCNAPP API access and `weasyprint` for HTML-to-PDF rendering [src: extensible-reporting-readme]. A separate PoC implementation plan prototypes a TypeScript/React/Express workspace (shared types, Express proxy, Puppeteer-based PDF renderer) as a possible successor architecture [src: poc-implementation].

**Scoring methodology.** The main gauge, `calcPostureScore`, is `100 − mean(findingRiskScores)` across one flat pool of Alerts, CVEs, Compliance, Identities, and Secrets, using the shared `SEVERITY_WEIGHTS = { critical: 100, high: 70, medium: 40, low: 10 }` table [src: scoring-guide]. CVEs only count toward the mean when `cveRiskScore ≥ HIGH_RISK_CVE_THRESHOLD (9.85)`; `cveRiskScore` is deliberately preferred over the sibling `riskScore` field (empirically different — one live CVE sat at 9.95 while its `riskScore` was 6.3) [src: claude-md]. A separate per-cloud score (`computeCspScores`) is rate-based rather than raw-count-based so an inventory-rich AWS account is not punished for having more surface area than a smaller Azure account [src: scoring-guide]. Correlated per-asset risk (`computeAssetRiskMap`) sums CIEM credential (+100), generic secret (+70), gated CVE (`×10`), and capped misconfiguration (`min(60, critCount×10)`) factors, normalizes 0–100, and bucketizes via `ASSET_TIER_THRESHOLDS = { critical: 75, high: 50, medium: 30 }` with an internet-exposure downgrade/upgrade [src: claude-md].

**FAIR-based risk framework integration.** The dashboard embeds a standalone ROI/FAIR calculator (`roi-calculator.html`) that opens pre-populated from live dashboard counts [src: claude-md]. The FAIR model drives the business case: `Annual Risk Exposure = (TEF × TC × S × (1−CS)) × LM`, with FortiCNAPP moving three levers — TEF −17% from hardened posture, S from 0.40 → 0.15 (−62%) from 2-minute Polygraph ML dwell time versus 48-hour industry baseline, and CS from 0.30 → 0.75 (+150%) from layered CSPM+CWPP+CIEM detection — yielding the headline $4.03M → $0.45M, 18× ROI, 3-week payback story used in CSO conversations [src: fair-framework-guide-for-cso].

**Docker deployment.** Container-first from day one: multi-stage `node:18-alpine` Dockerfile (~200 MB final image), `--cap-drop=ALL --cap-add=NET_BIND_SERVICE --cap-add=CHOWN` enforced via Linux file capabilities (`setcap`) because Docker does not propagate `--cap-add` into non-root exec's effective sets on this runtime [src: claude-md]. `/app/data` bind-mounts to a named `rca-cache` volume so cached findings survive `docker rm`; `entrypoint.sh` self-heals volume ownership and reuses a one-shot `/tmp/selfsigned/` cert across `docker restart` so visitors don't re-click past TLS warnings on every hot-deploy [src: claude-md]. Supported targets span Docker Compose, Swarm, Kubernetes (EKS/GKE/AKS), ECS Fargate, and Cloud Run [src: docker-deployment-guide].

**Intended field-use workflow.** The field flow is: SE logs into a live customer tenant, waits one refresh cycle while `refreshData()`'s two-phase fetch (Phase 1 parallel: alerts/vulns/identities/secrets/exposure-paths/attack-paths; Phase 2 throttled: compliance/secretsAll/publicStorage) populates the dashboard, walks the customer through the posture score and per-asset risk map, generates a sanitized PDF (`?sanitize=1` deterministically scrubs hostnames/ARNs/IPs/account IDs) [src: claude-md], and then opens the FAIR calculator to translate the findings into a dollar-denominated board-ready narrative [src: fair-framework-guide-for-cso]. Target: close a 2-week PoV with professional reports produced in roughly five minutes.

### Hosted RCA service: guided setup and lifecycle (newly ingested)

Four user-uploaded HTML files dated 2026-10-15 describe RCA as a **hosted, per-customer service** at `rca.fabriclab.ca` (a new service the user created and is launching), driven by a read-only FortiCNAPP API key. The deck is marked "Fortinet Internal". `(src: user-upload-rca-guided-setup-2026-10-15, user-upload-rca-scoping-checklist-documentation-2026-10-15)`

- **Data path:** customer cloud (AWS, Azure, GCP, agent or agentless workloads) -> FortiCNAPP tenant -> read-only API key -> a **private RCA instance per customer**. The RCA "never receives cloud credentials". `(src: user-upload-rca-diagram-2026-10-15)`
- **Scoping:** window of **7 or 14 days**; optional **sanitized copy**; findings correlated into four categories (high-permissive identities; internet-exposed resources with a critical vulnerability; critical alerts; secrets exposure).
- **Report styles (4):** Standard Technical; Wider-Scope Beta (per-cloud scoring, exploit-path simulation, per-host attack diagrams); Executive Overview; Narrative Beta.
- **Run steps:** create a read-only key in FortiCNAPP (**Settings > API Keys**), open `rca.fabriclab.ca`, fill the **New assessment** form (customer name, tenant address such as `tenant.lacework.net`, Key ID, Secret, optional sub-account), click **Create assessment**. The secret is entered only in that form.
- **Lifecycle:** status **Starting** passes six stages (Creating resources, Provisioning storage, Pulling image, Starting container, Waiting for health, Loading FortiCNAPP data), then **Ready** -> **Open** (up to 20 s to populate). The instance **expires after 48 h**; row actions are **Open**, **+48h** and **Destroy**. A stuck "Starting" points to a wrong Key ID, Secret or tenant address.
- **Score:** the **Cloud Security Risk Score** gauge is the same score as the posture score described in the Overview: higher means fewer risk findings and a more secure cloud (user-confirmed). It maps to four maturity levels: Foundational, Managed, Advanced, Optimized (sample shown: 37, Managed).
- **Report generation:** left panel **Generate Cloud Security Report**; form fields Requester, Company Logo, Specialist Conclusion.
- **One-time integration access** (only if FortiCNAPP is not yet onboarded): AWS administrative privileges; Azure Global Administrator + Owner on every monitored subscription; GCP Owner (project) or Organization Administrator + Logging Config Writer (organization), with billing enabled; FortiCNAPP Administrator. Never used for scanning.
