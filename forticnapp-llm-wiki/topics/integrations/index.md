# Integrations

Cloud provider onboarding: AWS, Azure, GCP, OCI.

## Scope

This page indexes **19** source documents routed to this topic.

## Synthesized content

FortiCNAPP connects to a cloud provider either at the **account/subscription/project/tenancy level** or at the **organization level**, with organization-level recommended whenever possible because new sub-accounts added later are picked up automatically [src: forticnapp-adminguide.md]. The four integration types available across providers are Configuration (CSPM foundation, resource inventory), Audit Logs (CDR via native management events), Agentless Workload Scanning (vulns, secrets, malware), and DSPM — DSPM is only supported for AWS and Azure and is configured through Terraform or the FortiCNAPP CLI rather than the console [src: forticnapp-adminguide.md]. Three deployment paths exist: **Automated configuration** (recommended; FortiCNAPP runs Terraform + cloud-native services under temporary credentials), **cloud-provider tools** (CloudFormation for AWS), and legacy/alternate paths — Guided Configuration (deprecated), CLI, raw Terraform, or Manual [src: forticnapp-adminguide.md]. The automated flow does preflight, Terraform plan/apply, custom-resource handling (e.g. Lambda), registration, validation, and then rolls back **all** selected types if any one fails [src: forticnapp-adminguide.md].

## AWS

AWS supports account- and organization-level integrations, plus a special AWS Control Tower path that is only available through CloudFormation [src: forticnapp-adminguide.md]. Automated configuration requires administrator credentials (temporary STS credentials from IAM Identity Center or an MFA-protected IAM user via `aws sts get-session-token` are recommended) [src: forticnapp-adminguide.md]. CloudFormation covers Configuration (single + Organization), CloudTrail, CloudTrail+Configuration (Control Tower), Agentless Workload Scanning (single + Organization), and EKS Audit Log; audit-log integrations provision an **SNS topic, SQS queue, and S3 bucket** for log ingestion, and the IAM role and S3 bucket must be collocated in the same account [src: forticnapp-adminguide.md]. CloudTrail analysis is restricted to management events (S3 object-level data events are excluded), and SSE-KMS-encrypted buckets need an explicit decrypt grant to FortiCNAPP [src: forticnapp-adminguide.md]. For organizations, `AWS CloudTrail account mapping` uses a JSON file (`defaultLaceworkAccountAws` + per-OU `aws_accounts` arrays) to route sub-accounts to FortiCNAPP sub-accounts [src: forticnapp-adminguide.md]. The CLI equivalent is `lacework generate cloud-account aws` (plus `aws controltower` and `k8s eks`) [src: forticnapp-adminguide.md].

## Azure

Azure integration is subscription- or tenant-level and is built around an **Entra ID App Registration + service principal** [src: forticnapp-adminguide.md]. The automated path requires temporary bootstrap credentials: `az ad sp create-for-rbac --role Owner --scopes /subscriptions/<id>`, a 1-hour `credential reset` (the **second** secret is the valid one — the first yields an invalid-secret error), and assignment of **Application Administrator + Privileged Role Administrator** in Entra, then paste Client ID / Secret / Subscription ID / Tenant ID into the console [src: forticnapp-adminguide.md] [src: FortiCNAPP-Azure-Single-Subscription-Logical-Assessment.md]. The manual path instead needs an explicit **Reader** role on each subscription (or inherited via a Management Group), **Key Vault Reader** (recommended) or Vault access-policy List permissions on keys/secrets for Configuration, and optional **Directory Reader** in Entra — without Directory Reader, IAM policies and Entra LQL datasources are not assessed [src: forticnapp-adminguide.md]. The portal "Assign Reader" procedure maps to the Manual path only; granting Reader to the Automated bootstrap SP is redundant because Owner already covers it [src: FortiCNAPP-Azure-Single-Subscription-Logical-Assessment.md]. An onboarding assistant exists that automates preflight, app-registration/SP creation, FortiCNAPP CloudAccount creation (with a dry-run write gate and KeyVault-backed secret references `kv:<vault>/<name>` so secrets never reach the LLM), and verification against `AzureCfg`/`AzureAlSeq` payloads [src: README.md] [src: CLAUDE.md]. CLI equivalent: `lacework generate cloud-account azure` [src: forticnapp-adminguide.md].

## GCP

GCP supports Configuration and Audit Log integrations at project or organization level, with the audit path split into **Pub/Sub-based** and **Storage-based** flavors [src: forticnapp-adminguide.md]. The user running the integration needs `roles/resourcemanager.organizationAdmin`, `roles/iam.organizationRoleAdmin`, `roles/logging.configWriter`, and optionally `roles/billing.user` at the organization level [src: forticnapp-adminguide.md]. The FortiCNAPP **service account** itself requires `roles/browser`, `roles/cloudasset.viewer`, `roles/iam.securityReviewer`, and a **custom role** (`lwOrgComplianceRole`/`lwComplianceRole`) carrying `bigquery.datasets.get`, `compute.projects.get`, `compute.sslPolicies.get`, `pubsub.topics.get`, and `storage.buckets.get` for Configuration; Pub/Sub audit logs add `roles/pubsub.subscriber` and `roles/monitoring.viewer`; Storage audit logs add `roles/storage.objectViewer` [src: forticnapp-adminguide.md]. Temporary credentials come from `gcloud auth print-access-token` (60-minute lifetime) [src: forticnapp-adminguide.md]. CLI: `lacework generate cloud-account gcp` and `lacework generate k8s gke` [src: forticnapp-adminguide.md].

## OCI

OCI is **Private Preview** and only supports the **Configuration** integration type — not Audit Log, not Agentless Workload Scanning [src: forticnapp-adminguide.md]. There is no automated or CloudFormation-equivalent path: onboarding is either `lacework generate cloud-account oci` (requires `TF_VAR_config_file_profile` set to a valid OCI CLI profile and the correct home region selected) or the **Manual** procedure, where you create a FortiCNAPP OCI user, add it to a group, and attach a policy with ~24 `inspect`/`read` verbs across `tenancy` scope — buckets, compartments, volumes, security-lists, users, groups, policies, domains, instances, subnets, network-security-groups, VCNs, route-tables, internet-gateways, load-balancers, compute-clusters, vnics/vnic-attachments, volume-attachments, leaf-certificates, cloud-guard-config, and tenancies [src: forticnapp-adminguide.md]. After integration, OCI access inside FortiCNAPP is governed by **resource groups** that align 1:1 with OCI compartments, assigned to FortiCNAPP roles and user groups [src: forticnapp-adminguide.md]. The matrix work-in-progress notes that CIEM, CWPP, KSPM (OKE), and DSPM on OCI remain unverified against official FortiCNAPP sources and should not be claimed GA [src: OCI_CSP_CNAPP_Matrix_WITH_FACT_CHECKS.md] [src: OCI_CSP_CNAPP_Matrix_TEMPLATE.md].

### Method choice and Azure paths (consolidated from the FortiCNAPP skills)

**Method.** *Automated configuration* is the default: FortiCNAPP runs preflight, Terraform plan and apply, registration, then switches to a scoped service identity, and rolls back all selected types if one fails; it needs temporary high-privilege credentials, supports Configuration, Audit log and Agentless, and does not cover DSPM [src: skill-forticnapp]. *Terraform or the FortiCNAPP CLI* (`lacework generate cloud-account <aws|azure|gcp|oci>`) suits IaC, many accounts, or DSPM (AWS and Azure only) [src: skill-forticnapp]. *Guided configuration* is deprecated for new integrations. Prefer organization-level integrations because they cover existing and future accounts. Configuration, audit log and agentless are agentless; process-level runtime detection on hosts and Kubernetes needs the FortiCNAPP agent [src: skill-forticnapp]. Console entry: Settings, Integrations, Cloud accounts, Add New [src: skill-forticnapp].

**Azure has three paths** [src: skill-forticnapp][src: skill-forticnapp-azure-integration]: (A) automated configuration, bootstrapped with a temporary service principal that has Owner on the subscription plus the Entra roles Application Administrator and Privileged Role Administrator, limited to a one-hour secret and deleted afterwards; (B) Terraform or CLI (`lacework generate cloud-account azure ... --apply`), using the `ad-application`, `config`, `activity-log`, `agentless-scanning`, `microsoft-entra-id-activity-log` and `dspm` modules; (C) manual app registration with Reader per subscription or once on a management group, Key Vault Reader for the Configuration integration, and an optional Directory Reader. Tenant-level automated permissions beyond subscription Owner, ingestion timings and the exact identity left by the automated flow are recorded as FACT NOT AVAILABLE in the skills. A helper script, `forticnapp-az-onboard.sh` (preflight, bootstrap, cleanup), is preserved in `skills/`.

**Open conflict (Azure permissions).** Two reference files in the Azure skill say Security Reader and Microsoft Graph application permissions with admin consent (`Directory.Read.All`, `User.Read.All`, `Group.Read.All`) are required, and that an integration stuck in PENDING usually lacks admin consent [src: skill-forticnapp-azure-integration]. The skill's own main file and the `forticnapp` skill state these are not in Fortinet's Azure app procedure and must not be requested unless a newer Fortinet source says so [src: skill-forticnapp][src: skill-forticnapp-azure-integration]. The two reference files carry no source tags, so treat them as unverified until checked against the Fortinet Administration Guide.

### Automated configuration (newly ingested)

FortiCNAPP's **Automated configuration** path (console: Settings → Integrations → Cloud accounts → Add New → <Provider> → Automated configuration) orchestrates **Terraform + cloud-native services** under the hood. It supports Configuration, Audit log, K8s audit log (AWS/GCP only), and Agentless Workload Scanning — **not DSPM**. Flow: preflight → Terraform init/plan → apply (optionally via CloudFormation StackSets for org-wide) → short-lived helpers (e.g. Lambda) for custom resources → registration/validation → runtime handoff from the admin creds to the deployed cross-account role or service identity. Rollback is **all-or-nothing** across selected integration types if any fails. Resources get tagged `lacework_tag=self-deployment` and `lacework_integration=<type>` (`agentless|cloudtrail|activitylog|auditlog|configuration|eks_audit_log|gke_audit_log`) — these are what you grep to delete after an integration is removed. For Azure, the created **App Registration** needs **Owner** on the subscription plus **Application Administrator + Privileged Role Administrator** in Entra ID. `(src: user-chat-automated-configuration-2026-10-14)`

### Azure resource provider registration (newly ingested, 2026-10-16)

A user-supplied quick guide covers checking and registering an Azure resource provider from Cloud Shell (Bash), using `Microsoft.CloudShell` as the example. The sequence is: `az account set --subscription <id>`, then `az provider show --namespace <ns> --query registrationState -o tsv` (`Registered`, `NotRegistered` or `Registering`), then `az provider register --namespace <ns> --wait` if needed, then re-check. Registering needs Subscription Owner, Contributor, or a custom role with the registration permission. A short script registers the provider only when its state is not `Registered`; `az provider list` shows the state of all providers. `(src: user-chat-azure-resource-provider-registration-quick-guide-2026-10-16)`

The source does not say which providers a FortiCNAPP Azure integration needs, so this is general Azure background, not a documented FortiCNAPP prerequisite. Its Microsoft documentation link was text only and was not checked.
