## Overview

FortiCNAPP day-2 operations center on turning raw cloud telemetry into actionable incidents while keeping noise low. The alerting pipeline chains together **Alert Rules**, **Alert Profiles**, **Alert Channels**, and **Resource Groups** so that policy violations and anomalies are scoped to the right assets, phrased in the right language, and routed to the right responders — then promoted into **Composite Alerts** when they correlate, and finally handed to analysts with **AI-assisted triage**.

**Alert Profiles** are the mapping layer that turns an LQL policy's result columns into human-readable event text. Each profile is bound to a datasource and defines three parts: `fields` (datasource columns eligible for mapping — columns not listed are dropped from event detail), `description keys` (placeholders such as `{{RESOURCE_ID}}`; a field must have a key to appear in the alert), and `alertTemplates` with `name`, `eventName`, `subject`, and `description` strings `[src: alert-profiles.md]`. Policies reference a profile and template as `alertProfileId.alertTemplateName`, falling back to the default template if the named one is missing `[src: alert-profiles.md]`. Predefined profiles exist per datasource — `LW_CFG_AWS_*`, `LW_HA_DNS_REQUESTS`, `LW_HE_CONTAINERS/FILES/IMAGES/MACHINES/PROCESSES/USERS`, and `CloudTrailRawEvents` — and custom profiles can extend any parent other than `LW_LPP_BaseProfile` (which carries no alerts) via `POST /api/v2/AlertProfiles`; custom fields and description keys are not supported through the API, only custom templates `[src: alert-profiles.md]`.

**Resource Groups** scope policies, alerts, and reports to subsets of the environment. A group has a `resourceType` (AWS, Azure, GCP, container, machine, Kubernetes, OCI) and a `query` composed of named `filters` (`field`, `operation`, `values`, optional `key`) joined by an AND/OR `expression` tree with one operator per level — nest groups for mixed logic `[src: resource-groups.md]`. Operations include `STARTS_WITH`, `INCLUDES`, `ENDS_WITH`, and `EQUALS` (the resource-group and AWS-account fields are `EQUALS`-only), and tag/label fields require a `key` `[src: resource-groups.md]`. Filterable fields vary by type: AWS exposes Account, Organization ID, Resource Tag(key) and Region; Kubernetes exposes CSP, Cluster Name and Namespace among others `[src: resource-groups.md]`. Groups can be managed via Console, API, or Terraform (the newer unified `lacework_resource_group` resource replaces the per-cloud ones); treat the apparent deprecation of organization-level groups as unconfirmed and check current docs `[src: resource-groups.md]`.

**Composite Alerts** sit above individual detections. Rather than firing on a single event, FortiCNAPP aggregates multiple indicators tied to the same entity over a defined correlation window — minutes or hours, not milliseconds — to raise detection fidelity, catch multi-step chains earlier, and present analysts a pre-assembled narrative `[src: improving-cloud-intrusion-detection-and-triage-with-forticnapp-composite-alerts-2026-10-13.md]`. Each alert is delivered as an **Observation Timeline** of ordered observations (behavior type, first/last-seen timestamps, source IPs and geolocation, newly-used APIs, mismatched user agents, novel command lines, unexpected container or VM changes) tied to the involved users, machines, containers, and cloud services `[src: improving-cloud-intrusion-detection-and-triage-with-forticnapp-composite-alerts-2026-10-13.md]`. The **Intrusion Graph** complements the timeline by compacting the most important relationships into a readable graph, deliberately separating "suspicious access" from "suspicious action" stages because their co-occurrence sharply raises intrusion likelihood; shared behaviors across machines or identities are aggregated into a single node while uniquely significant entities (for example a lone jump host) are held out `[src: composite-alerts-intrusion-graph.md]`.

The **Log4j host + stolen AWS keys** vendor walkthrough illustrates the flow end-to-end. A contractor's EC2 instance fires a Potentially Compromised Host alert — internet-exposed, two active vulnerabilities (the code-aware agent confirms the vulnerable code actually runs), local enumeration, stored-credential access, a reverse shell, and traffic to ports 4444/1389/8088 matching Log4j against a Java Spring Boot app running as root — leading to quarantine, snapshot, and stop `[src: composite-alerts-walkthrough-log4j-and-stolen-keys.md]`. A second composite alert — Potentially Compromised AWS Keys — shows Tor logons, discovery API calls, and a `CreateDBSnapshot` call indicating possible exfiltration; containment revokes session credentials, adds explicit deny on the role, and rotates keys `[src: composite-alerts-walkthrough-log4j-and-stolen-keys.md]`. The same environment would have been flagged earlier by the attack-path dashboard, the security graph, and the Identities dashboard (296 EC2 permissions assigned, only 2 used) `[src: composite-alerts-walkthrough-log4j-and-stolen-keys.md]`.

**AI-assisted triage** (FortiCNAPP AI Assist) sits on top of composite alerts. Entry actions are **Triage** (fast severity/scope/first-step), **Incident Report** (ranked findings, entity tables, timeline, confidence, pasteable into tickets or Slack, exportable as Markdown), and **Remediate** — with remediation tied to actual entities ("rotate the access key for identity X used from anomalous IP Y") rather than generic playbooks `[src: ai-assisted-alert-triage.md]`. The assistant follows a consistent IR flow (verify/scope → contain if needed → eradicate → recover → harden), surfaces an "if you can only do one thing" step, avoids disruptive actions until compromise is validated, and separates facts from hypotheses with explicit confidence and data gaps `[src: ai-assisted-alert-triage.md]`.
