## Synthesized content

## Overview

FortiCNAPP exposes its platform to large-language-model clients through a Model Context Protocol (MCP) server surface and a growing family of agent patterns that drive those tools from natural language. The core piece is the `mcp__forticnapp__*` tool family generated from `lw.yaml` (the FortiCNAPP/Lacework API 2.0 OpenAPI definition); the tools are typically deferred and must be loaded by the client with `ToolSearch` using `select:<tool_name>` before they can be called [src: SKILL.md]. Every `*_search` tool shares a common body shape — `filters` (list of `{field, expression, value|values}` using a verified operator enum where negation is `ne` and `not_eq` does not exist), `returns` (field projection, mandatory on wide inventory rows to avoid blowing the response size limit), `timeFilter` (defaulting to the last 24h and capped at 7 days), and `page_url` for pagination that now auto-chunks oversized responses behind an opaque cursor instead of simply erroring out [src: SKILL.md]. Inventory search has a well-known footgun: its `dataset` parameter is legacy and silently ignored for resource-type selection, so scoping must be done with a `filters` entry on `resourceType` (lowercase `service:resource` strings such as `ec2:instance`), and `paging.totalRows` counts snapshot rows rather than distinct resources, so client-side dedupe on `resourceId`/`urn` is required [src: SKILL.md].

The LQL agent sits one layer above this surface and turns a security intent into a validated, tested FortiCNAPP LQL query. It runs a five-phase flow — Understand, Datasource-first discovery, Draft 1, a bounded loop of up to 8 iterations against `lql_validate`/`lql_execute`/`lql_cache_search`/`lql_find_policy_queries`/`lql_describe_datasource`, Display, Remember — and scores each candidate from 0 to 1 across syntax, schema, execution, intent-match and relevance; it stops at 0.90 or on circuit-breakers for no-progress, repeat queries, or limit-hit results, and caches successful candidates back to `lql.cache` [src: lql-agent.md]. The agent is read-only, treats tool results as ground truth over its own memory, and encodes a long list of tenant-specific LQL rules (no `count(*)`, no `split_part`, bracket-indexed JSON arrays rejected, booleans compared as strings, `with` as a left outer join, semi-joins via `x::String in { ... }`) [src: lql-agent.md].

Beyond LQL, the `mcp-agent` project generalizes this pattern as a standalone terminal agent that launches any stdio MCP server as a subprocess, discovers its tools at runtime via `tools/list`, and drives them from natural language. It reuses the lql-agent's synchronous Anthropic tool-use loop, bridges the MCP SDK's async `ClientSession` through a dedicated background event-loop thread so the REPL/TUI stay synchronous, and defaults to read-only — classifying tools by MCP annotations first and a `READ_VERBS` heuristic (`get, list, search, read, describe, fetch, show, find, query, count, lookup`) second, with unknown verbs failing safe to `write` and hidden behind `--allow-write` [src: 2026-08-02-mcp-agent.md].

Web/UI agents follow the same shape over HTTP: the `webaiagent` Chrome extension adds a Cloud Investigation tab whose Dockerized `serve.py` spawns `python3 -m forticnapp_mcp.main` as a persistent subprocess and speaks newline-delimited JSON-RPC 2.0 directly from stdlib Python (no `mcp` SDK import). A `POST /mcp/investigate` endpoint runs a tool-use loop capped at 6 iterations, hardcodes `ENABLE_MUTATION_TOOLS=false`, serializes all access behind one lock, and streams NDJSON progress events into the drawer's chat log [src: 2026-07-07-cloud-investigation.md].

For live demos, the FortiCNAPP AIOps 5-act script wires Claude Desktop → Claude LLM → MCP Server (FastMCP/Docker on `:8000/sse`) → `lacework` CLI → FortiCNAPP backend, walking from a cached `lookup_query` hit, to full LQL generation (`get_lql_reference` → `validate_lql` → `run_lql` → `report` → `save_query`), to REST API enrichment via `forticnapp_api` and a curated `get_forticnapp_api_catalogue`, to LQL+API correlation on shared host ARNs, to an in-process `threat_model` that maps MITRE ATT&CK stages to Fortinet defensive controls [src: DEMO_GUIDE.md]. A separate FortiCNAPP Cloud Integration agent sits alongside these: it is a documentation-driven onboarding specialist that parses provider/capability/method/scope from the user's question, retrieves procedures from `knowledge.md`, and emits a strict Understanding/Recommended Approach/Prerequisites/Steps/Commands/Validation/Troubleshooting/Next Question response, with hard safety rules against exposing secrets, mixing providers, or inventing destructive steps [src: forticnapp-integration-agent.md].
